# 📘 Motion Community — GitHub Rules

**Версия:** 1.0

**Применяется к:** всем участникам Motion Community

## 1. Общие положения

GitHub Organization Motion Community является централизованным пространством для совместной разработки и хранения проектов сообщества.

Каждый участник обязан соблюдать правила работы с кодом, репозиториями, задачами и информационной безопасностью.

## 2. Доступ к GitHub

- Каждый участник использует собственный GitHub-аккаунт.
- Передача паролей и токенов другим участникам запрещена.
- Доступ предоставляется руководителем или уполномоченным администратором.
- Участник получает только необходимые для работы разрешения.
- При выходе из команды доступ к репозиториям организации отзывается.

## 3. Правила работы с ветками

Основные ветки:

- `main` — стабильная версия проекта.
- `develop` — интеграционная ветка, если она используется в проекте.
- `feature/*` — разработка новых функций.
- `fix/*` — исправление ошибок.
- `hotfix/*` — срочные исправления.
- `docs/*` — изменение документации.

Примеры названий:

```text
feature/attendance-dashboard
fix/login-validation
docs/api-instructions
```

Каждая задача должна разрабатываться в отдельной ветке.

## 4. Правила коммитов

Используем понятные сообщения в формате:

```text
type: description
```

Поддерживаемые типы:

- `feat` — новая функциональность.
- `fix` — исправление ошибки.
- `refactor` — изменение структуры без изменения функциональности.
- `docs` — документация.
- `test` — добавление или изменение тестов.
- `chore` — технические работы.
- `perf` — оптимизация производительности.

Примеры:

```text
feat: add student dashboard
fix: resolve authentication error
refactor: optimize database queries
```

Коммиты вида `update`, `123`, `final`, `asdf` не допускаются.

## 5. Pull Request

Перед объединением изменений необходимо:

1. Убедиться, что задача выполнена.
2. Проверить работоспособность кода.
3. Запустить применимые тесты.
4. Создать Pull Request.
5. Описать внесённые изменения.
6. Указать связанную задачу.
7. Отправить изменения на Code Review.

Изменения в `main` должны попадать через проверенный Pull Request.

Самостоятельное объединение изменений без согласования запрещено внутренним регламентом.

## 6. Code Review

Team Lead или назначенный reviewer проверяет:

- Корректность логики.
- Качество и читаемость кода.
- Безопасность.
- Архитектуру.
- Обработку ошибок.
- Влияние на существующую функциональность.
- Результаты тестирования.

Если обнаружены проблемы, автор обязан внести исправления.

## 7. Работа с задачами

Перед началом разработки необходимо иметь согласованную задачу в GitHub Issues или командном трекере.

Рекомендуемые статусы:

- Backlog
- Todo
- In Progress
- In Review
- Testing
- Done
- Blocked

У каждой задачи должны быть ответственный исполнитель, описание и критерии готовности.

## 8. Безопасность

Строго запрещено:

- Добавлять `.env` с секретами в репозиторий.
- Публиковать API-ключи, токены и пароли.
- Загружать базы данных с персональными сведениями без разрешения.
- Передавать приватные репозитории посторонним.
- Использовать чужие учётные записи.
- Открывать приватный проект без согласования.
- Самостоятельно изменять production-инфраструктуру без полномочий.

При обнаружении утечки или уязвимости необходимо немедленно сообщить ответственному Team Lead или администратору. Порядок конфиденциального сообщения описан в [SECURITY.md](https://github.com/motion-community/.github/blob/main/SECURITY.md).

## 9. Правила для стажёров

- Стажёр работает в пределах назначенных репозиториев.
- Каждую задачу контролирует наставник.
- Все изменения проходят Code Review.
- Самостоятельный деплой в production запрещён.
- По результатам испытательного периода определяется дальнейшая роль участника.

## 10. Ответственность

Участники отвечают за соблюдение правил в пределах своей роли.

Нарушения рассматриваются руководителями Motion Community. В зависимости от обстоятельств доступ может быть временно ограничен или отозван.
